# Rust allocation source experiment: build blocked, no runtime support

This is **unqualified source work**, not a compiled runtime, transport fix or benchmark result. The stock task116 diagnostic still has 32 correct numerical actions and 32 unsupported graph responses. Historical reports and engine behavior are unchanged. Engine source remains `f868915bdbe72c14fe3f8fb0be3e7228cda7be41dfb7b9255775347823d64410`.

The pinned Qiskit 2.4.2 source lock uses Rust NumPy **0.28.0**, not the latest documentation version. The verified PyPI archive has 4,089,826 bytes and SHA-256 `b9844e28336fdbed0d53f8cf82a681d0365574dd68d04ef877d1619971462ad6`; its Cargo.lock matches the official tag byte for byte (`02460712f52341f3b9e45522fbbf3a0d30407234d146b00843a39ef4f6dd4d6f`). The locked crate archive matches checksum `778da78c64ddc928ebf5ad9df5edf0789410ff3bdbf3619aed51cd789a6af1e2`. Sources: [Qiskit PyPI metadata](https://pypi.org/pypi/qiskit/2.4.2/json), [official lock](https://raw.githubusercontent.com/Qiskit/qiskit/2.4.2/Cargo.lock), [pinned owner source](https://docs.rs/numpy/0.28.0/src/numpy/slice_container.rs.html).

That owner privately holds a typed Box/Vec destructor, pointer, initialized element length and reserved capacity. Reserved capacity can exceed initialized length. Reading capacity bytes would expose uninitialized memory; an ndarray's logical nbytes alone cannot establish either extent. The source experiment adds private immutable provenance at those allocation constructors and a weak original-root reference before exposure. Original typed destructors remain in place. Fixed helpers inspect, read/write initialized bytes, reconstruct actual owners and construct bounded numeric aliases. Their descriptor separates initialized bytes from allocated bytes; the wire-facing API accepts no addresses or destructor names. Unknown types remain unsupported. The experiment restricts loading to CPython 3.12.

[Eight source-patch controls](patch-controls.xml) passed, with zero failures/errors/skips in **0.224 JUnit seconds**. They exercise hash checking of every modified upstream input, refusal before writes on any mismatch, existing destination protection, refusal of a second application, source-directory restrictions, unchanged original lock/destructors and exact output identities. The [manifest](source-patch.json) records modified file hashes and patch-script identity. These are patch-process tests, not execution of the native helpers.

All **35 required native controls** collect successfully but remain **unrun**. They cover four numeric allocation types and both allocator kinds, spare capacity, weak-root destruction, retained aliases, readonly roots, negative/empty/overlapping geometry, invalid extents, spoofed owners and forbidden dtypes, plus actual Qiskit Pauli output against a literal tensor oracle. A [stock-runtime required control](stock-required-control.txt) exited 1 at the missing profile assertion as intended; it does not silently skip or assert native support.

The separate allocator harness build stopped before type checking the added Rust module: Windows Application Control blocked the generated PyO3 0.28.2 `build-script-build` with **os error 4551**. Rust 1.98.1 and Cargo 1.98.1 were observed. The harness has its own recorded lock, whose other dependency versions differ from the Qiskit workspace lock; it could not qualify the actual Qiskit extension even if it compiled. No adapted wheel or actual Qiskit build was produced. Later source refinements have syntax checks only. The policy was not changed and the blocked executable was not retried or relocated.

Read-only review found no actionable source issue after inspecting pinned APIs, lifetimes, owner/root links, initialized storage bounds and NumPy base behavior. Rust formatting/syntax checks and Ruff lint/format checks passed for the active engine tree plus the three added Python native files (246 files formatted). These do **not** establish Rust type checking, native execution, concurrency safety or memory-sanitizer coverage. The [verification report](verification.json), SHA-256 `e0a2ad6a7487dd8af5d69122c8d625b2cf7c42e1e0bfb74c18337adf458646f6`, explicitly leaves every runtime/transport/admission gate false.

From `engine/`, with already verified source archives extracted into sibling directories named `qiskit-2.4.2` and `numpy-0.28.0`, source-patch controls can be repeated without compiling:

```sh
GRAYBENCH_RUST_SOURCE_CACHE=VERIFIED_CACHE python -m pytest native/tests/test_qiskit_rust_patch.py
python native/patch_qiskit_rust.py FRESH_SOURCE/qiskit-2.4.2 FRESH_SOURCE/numpy-0.28.0
```

The cache variable syntax above is for a POSIX shell; in PowerShell assign it using `$env:GRAYBENCH_RUST_SOURCE_CACHE`. Verify complete source archives before trusting a runtime build: the patch preflight checks only the files it modifies and the original lock. Do not patch stock installed environments. A permitted build environment must first compile and execute the allocation controls, then build actual Qiskit under an audited adapted lock. Separate graph codecs, transactional/adversarial controls, all 32 canonical replays, sanitizer checks, isolated execution, toolchain locking and independent admission remain required by the [plan](../../../superpowers/plans/2026-10-07-rust-owned-storage.md). No graph codec was enabled and no reference was accepted on the strength of this source experiment.


A clean checkout of `798e9fb`, with a separately installed locked environment on the same Windows host and the shared verified source cache, reproduced **eight passes, zero failures/errors/skips** in **0.220 JUnit seconds**. The source patch manifest reproduced byte for byte; all four added code-file hashes, active engine source and committed evidence bytes matched. Lint/format checks passed for 246 Python files and Rust syntax/format checks passed. The checkout remained unchanged. The [clean report](clean-verification.json), SHA-256 `0094f4ca6696d53f6c784cc4b56680d4d5ae046b2c5b70e810fffac53a2be482`, and [JUnit output](clean-patch-controls.xml) preserve this bounded reproduction.
